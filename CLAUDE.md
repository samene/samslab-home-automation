# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sam's Lab is a secure, offline-capable home-automation platform: a FastAPI cloud server (control plane, system of record) paired with a Raspberry Pi agent (edge execution plane) over an outbound-only, versioned WebSocket protocol. The cloud server has real implementation; the agent has real implementation for its camera plugin (live streaming + snapshot capture) but is otherwise a reserved boundary. Within the server, four business domains are built out — **Device Registry** (`server/app/domains/devices/`), **Commands** (`server/app/domains/commands/`, the central business domain — every action a device performs is represented as a command), **Auth** (`server/app/domains/auth/`, JWT authentication + RBAC for both human users and devices; no REST route requires it yet, but the WebSocket Gateway does), and **Snapshots** (`server/app/domains/snapshots/`, camera still-image metadata — hard-deleted, unlike the other three, since a snapshot's whole point is a real S3 object) — plus an **application layer** (`server/app/application/`, not a domain itself) that is the only place a workflow spanning more than one of them is allowed to live, a **WebSocket Gateway** (`server/app/websocket/`, transport only — see its own section below) that is the one implemented transport for agent connections, and a **Command Dispatcher** (`server/app/dispatcher/`, coordination only — see its own section below) that delivers commands to connected devices over that gateway and tracks their acknowledgement/execution. Treat the four domains and the application layer as the reference pattern for every future domain/use case. Everything else (`shared/`, and the server's `scheduler/`, `storage/`, `metrics/`, `repositories/`, `models/` packages, plus every agent plugin besides `camera`) is a reserved boundary with no logic yet; don't fill them in speculatively.

## Commands

Run everything from the repo root; the server package lives under `server/` (`pythonpath = server` in pytest config, `--app-dir server` for uvicorn).

```bash
python3.13 -m pip install -e '.[dev]'   # install server + dev deps
pre-commit install                       # one-time, enables ruff hooks on commit

make run          # uvicorn app.main:create_app --factory --reload
make test         # pytest (testpaths = server/tests)
make lint         # ruff check server
make format       # ruff format server
make typecheck    # mypy (strict, server/app + server/tests)
make docker-up    # docker compose up --build -d (server + postgres + victoriametrics + grafana + minio)
make docker-down
make clean        # remove __pycache__/.pytest_cache/.mypy_cache/.ruff_cache
```

Run a single test: `pytest server/tests/test_devices.py::test_name -v` (or `test_commands.py`, or one of the `test_auth_*.py` files — jwt/passwords/tokens/repository/service/dependencies/rbac/api/application_service, split by concern rather than one large file).

`make coverage` runs `pytest --cov=app --cov-report=term-missing` (needs `pytest-cov`, in the `dev` extras; `pyproject.toml`'s `[tool.coverage.run]` sets `concurrency = ["thread"]`, needed because `TestClient`'s websocket support runs the ASGI app on a separate portal thread). Domains and the application layer are expected to stay at or above 95% coverage; a handful of multi-line `return Model(...)` statements show up as false-negative "missing" lines in the report — a real gap always has a passing-assertion-free line, so verify before chasing one.

Alembic migrations (target metadata is the shared `app.core.database.Base`; `alembic/env.py` imports every domain's `models` module so its tables register before `Base.metadata` is read):

```bash
alembic upgrade head
alembic revision --autogenerate -m "description"
```

Configuration is `pydantic-settings` reading environment variables / an untracked `.env` (see `server/app/config/settings.py` for the full field list — `SERVER_NAME`, `ENVIRONMENT`, `DATABASE_URL`, `JWT_SECRET`, `JWT_ALGORITHM`, `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_ACCESS_TOKEN_TTL_SECONDS`, `JWT_REFRESH_TOKEN_TTL_SECONDS`, `JWT_CLOCK_SKEW_SECONDS`, `S3_*`, `VICTORIA_METRICS_URL`, `WEBSOCKET_PATH`, `WS_HEARTBEAT_INTERVAL_SECONDS`, `WS_HEARTBEAT_TIMEOUT_SECONDS`, `WS_IDLE_TIMEOUT_SECONDS`, `WS_HELLO_TIMEOUT_SECONDS`, `WS_OUTGOING_QUEUE_SIZE`, `WS_MESSAGE_ACK_TIMEOUT_SECONDS`, `WS_MESSAGE_ACK_MAX_RETRIES`, `DISPATCHER_POLL_INTERVAL_SECONDS`, `DISPATCHER_DISCOVERY_BATCH_SIZE`, `DISPATCHER_ACK_TIMEOUT_SECONDS`, `DISPATCHER_EXECUTION_TIMEOUT_SECONDS`, `DISPATCHER_MAX_RETRIES`, `DISPATCHER_RETRY_BACKOFF_BASE_SECONDS`, `DISPATCHER_RETRY_BACKOFF_MAX_SECONDS`, `DISPATCHER_SWEEP_INTERVAL_SECONDS`, `ALLOW_ORIGINS`, `CAMERA_SNAPSHOT_COMMAND_TIMEOUT_SECONDS`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET`, `AWS_PRESIGNED_URL_TTL_SECONDS`, etc.). `DATABASE_URL`, every `JWT_*` field, every `WS_*` field, and every `DISPATCHER_*` field are consumed (by the Auth domain, the WebSocket Gateway, and the Command Dispatcher respectively); the server's `AWS_*` fields back `app/core/s3_client.py` (presigned URLs + delete, for `GET`/`DELETE /snapshots`) — a separate, least-privilege credential from the agent's own `AWS_*` settings, which only ever need `PutObject`; `S3_*`/`VICTORIA_METRICS_URL` remain reserved for future adapters.

## Architecture

**Clean Architecture, enforced by package boundaries, not just convention.** Dependencies point inward: delivery adapters → application services → repository/driver ports → infrastructure. Domain and application code must never import FastAPI, SQLAlchemy, GPIO libraries, WebSocket clients, or cloud SDKs directly outside the designated adapter files. This is the rule most worth checking before adding an import.

**Per-domain vertical slice.** Each business domain under `server/app/domains/<name>/` owns its full stack and only talks to the rest of the app through typed interfaces:

| File | Role |
| --- | --- |
| `models.py` | SQLAlchemy `DeclarativeBase` models (persistence only, domain-private) |
| `schemas.py` | Pydantic request/response contracts with field validators (the API boundary) |
| `repository.py` | All persistence queries for the domain; takes a caller-owned `AsyncSession` so the caller controls the transaction |
| `service.py` | Use-case orchestration and business invariants; depends on its own repository only — never another domain's repository or service, never SQLAlchemy directly, never FastAPI |
| `exceptions.py` | Domain-specific errors (a `<Domain>DomainError` base + subclasses) — never raise `HTTPException` from a service |
| `api.py` | FastAPI `APIRouter`; resolves a per-request, transaction-scoped **application service** via `Depends`, commits on success / rolls back on exception — contains no business logic itself |

Commands additionally has `validators.py` (reusable field-validation functions called from `schemas.py`) and `events.py` (the closed `CommandEventType` enum) — pull shared, non-trivial validation/constant logic into its own file like this rather than inlining it in `schemas.py` once a domain has enough of it to warrant the split. None of the four domains has a `mapper.py` — mapping a persisted model to a response shape is the application layer's job (see below), not the domain's. Snapshots is the one domain with no `schemas.py`: a snapshot is never created from an external request body (only from a completed `camera.snapshot` command's result, via the application layer), so there is no request shape for that domain to validate.

Auth extends the shape further with `jwt.py` (encode/decode, no FastAPI), `passwords.py` (Argon2 hash/verify), `tokens.py` (opaque refresh-token/client-secret generation + hashing), `permissions.py` (the `ROLE_PERMISSIONS` map — string permissions, never hardcoded per-endpoint checks), and `dependencies.py` (`CurrentUser`/`CurrentDevice`/`RequireRole`/`RequirePermission` — the one FastAPI-specific file besides `api.py`, kept separate because other domains' future controllers will `Depends()` on it directly). `service.py`'s `decode_principal()` is a module-level pure function, not a method, specifically so it needs no repository/session — token validation should never cost a database query.

Follow this exact shape when adding a new domain.

**Domains never call each other; the application layer is the only place that's allowed.** `server/app/application/` sits between REST and the domains and is not a domain itself. `CommandApplicationService` depends on both `DeviceService` and `CommandService` to enforce "a command's target device must exist and be enabled"; `AuthApplicationService` depends on both `AuthService` and `DeviceService` to enforce "a device must exist before it gets a credential"; `CameraApplicationService.capture_snapshot()` depends on `CommandApplicationService`/`DeviceApplicationService` (to dispatch and await `camera.snapshot`, exactly like `start_stream`/`stop_stream`) plus the Snapshots domain's own `SnapshotService` (to persist the completed command's result as metadata) — in every case a rule that belongs to neither domain individually, but no domain service ever imports or calls another domain's service or repository. A controller (`api.py`) depends only on its matching application service, never on a domain service or repository directly. See `server/app/application/services/` for `DeviceApplicationService`, `CommandApplicationService`, `AuthApplicationService`, `HealthApplicationService`, `CameraApplicationService`, `SnapshotApplicationService`, and `docs/architecture/COMPONENTS.md` for the full package breakdown (`dto/`, `mappers/`, `exceptions/`, `events/`, `validators/`, `interfaces/`). `SnapshotApplicationService` is the only place a presigned S3 URL is ever minted (`GET /snapshots`, `GET /snapshots/{id}`, via `app/core/s3_client.py`) — `CameraApplicationService.capture_snapshot()` never touches S3 itself, only metadata.

**No module-level singletons.** `create_app(settings)` in `server/app/main.py` is the only application entrypoint; it builds a fresh `dependency-injector` `ApplicationContainer` (`server/app/core/container.py`) per call and attaches it to `app.state.container`. Tests and production both go through this factory — never construct a module-level `FastAPI()` or a global DB engine. Route handlers pull infrastructure via `Depends` (shared providers like `get_database`/`get_event_bus` live in `app/dependencies/`, not duplicated per domain). The container also owns the per-application `EventBus` singleton (`providers.Singleton(EventBus)`).

**Errors are RFC 7807 problem+json, and REST only ever sees `ApplicationError`.** `server/app/core/problems.py` defines `ProblemDetails` and generic handlers. `main.py` registers exactly one domain-agnostic handler, `application_exception_handler`, for `app.application.exceptions.ApplicationError` and its five subclasses (`NotFoundError`→404, `ConflictError`→409, `ApplicationValidationError`→422, `ForbiddenError`→403, `UnauthorizedError`→401 with a `WWW-Authenticate: Bearer` header). Every application service is responsible for catching its domain services' exceptions and calling `translate_domain_error()` before they escape — a domain's own exception types (`DeviceDomainError`, `CommandDomainError`, `AuthDomainError`, ...) must never reach `main.py` or a controller. Add a new domain exception's translation to `app/application/exceptions/translation.py`'s map, not a new per-domain handler. `auth/dependencies.py` raises `UnauthorizedError`/`ForbiddenError` directly (it's a delivery-boundary file, like `api.py`) rather than a domain exception, since token/role/permission checks aren't really domain business logic.

**Explicit state machines for anything with a lifecycle.** Commands are immutable once created — the payload never changes, only `status` (and the timestamps that go with a transition) evolve, and only through a plain `dict[Status, frozenset[Status]]` transition table plus a single `ensure_transition_allowed()` check (`commands/service.py`, `ALLOWED_TRANSITIONS`) that every mutating service method calls first. Every transition also appends an immutable event row rather than mutating history. Follow this pattern (explicit table + guard function, not scattered if/elif chains) for any future domain with lifecycle states.

**Structured observability is mandatory at the boundary.** `RequestContextMiddleware` (`server/app/middleware/request_context.py`) generates/propagates `X-Request-ID` and `X-Correlation-ID`, binds them via `structlog` contextvars (`app/logging/context.py`), and logs one structured event per request including on exception. Any new service-boundary code should log through `structlog`, never with bare `print`/stdlib `logging`, and never log secrets or tokens.

**Soft-delete + audit-friendly persistence.** The Device Registry pattern (see `repository.py`) is: `deleted_at` timestamp instead of hard delete, `selectinload`/`lazy="selectin"` for relationships to avoid N+1s, explicit `flush()` (+`refresh()` only when a column has a DB-computed `onupdate`/`server_default` that would otherwise sit expired) after mutation, and narrow "allowed field" update methods (e.g. `update_last_seen` only touches heartbeat fields) rather than a generic setter for everything. Commands never update rows in place at all — see the state-machine note above. Snapshots is a deliberate exception to soft-delete: `DELETE /snapshots/{id}` hard-deletes the row (`session.delete`, not a `deleted_at` timestamp), because a snapshot's whole point is a real S3 object — `SnapshotApplicationService.delete_snapshot` deletes both S3 objects (best-effort; a missing/misconfigured S3 client only logs a warning, it never blocks the DB delete) before removing the row.

**Auth is transport-independent and never costs a query to authorize.** `auth/jwt.py`, `passwords.py`, `tokens.py`, `permissions.py`, and `service.py` import nothing from FastAPI — the same `AuthService`/`decode_principal()` back both REST and the WebSocket Gateway, and could back a future gRPC/MQTT transport too. A JWT's `role`/`permissions` claims are resolved and flattened at issuance time (`permissions_for_roles()`), so `RequireRole`/`RequirePermission` check already-decoded claims, never the database. Access tokens are short-lived, stateless JWTs; refresh tokens are the opposite — long-lived, opaque random strings, stored only as a SHA-256 hash (never a JWT, never the plaintext) — and every `POST /auth/refresh` **rotates**: the presented token is revoked in the same transaction the new pair is issued, so replaying an old refresh token fails immediately. Devices don't use refresh tokens at all; they hold an RSA private key permanently (never transmitted, never stored server-side — only the matching public key is) and sign a short-lived JWT assertion with it to get a fresh token via `POST /auth/device/token` whenever they need one, the JWT-bearer/`private_key_jwt` client-assertion pattern — this is what lets the agent's `ConnectionManager` request a brand-new token on every single connection attempt (see `agent/app/connection/token_provider.py`), so a reconnect never fails just because the previous access token's short TTL had elapsed. Comparing a persisted timestamp against `datetime.now(UTC)` in Python (not in a SQL `WHERE` clause) breaks on SQLite, which drops tzinfo on round-trip — push that comparison into the query instead (see `find_active_refresh_token_by_hash`'s `expires_at > as_of` predicate) rather than fetching the row and comparing in Python.

**The WebSocket Gateway (`server/app/websocket/`) is transport only — same rule as a domain's `api.py`, but for one persistent connection instead of one request.** It never executes a command, never touches GPIO, and never accesses a repository directly; its one cross-domain call is `DeviceApplicationService` (confirming a device is enabled at handshake time, and keeping `last_seen`/`status` current), the same Application Layer seam REST uses. `gateway.py`'s `handle_connection()` accepts unconditionally, then requires `HELLO` (carrying a device JWT) within `WS_HELLO_TIMEOUT_SECONDS`, negotiates the envelope's own `protocol_version` against `protocol.py`'s `SUPPORTED_PROTOCOL_VERSIONS`, and registers exactly one `Session` per `device_id` in the in-memory (never persisted) `SessionManager` — a second connection attempt for an already-connected device is rejected, not queued or evicted. `COMMAND`/`EVENT`/`LOG` are parsed, logged, and generically acknowledged (`MESSAGE_ACK`) by `handlers.py`; `COMMAND_ACK`/`COMMAND_RESULT` get the same generic ack *plus* publish `CommandAckReceived`/`CommandResultReceived` on the shared event bus — the gateway still never imports or calls the Command Dispatcher (see below) directly, it only publishes. `metrics.py`'s module-level `prometheus_client` `Counter`/`Gauge`/`Histogram` objects are a deliberate, narrow exception to "no module-level singletons": metrics are conventionally process-global, defined once at import time, so they're safe to share across every `create_app()` instance in one process (e.g. one per test) — any test asserting on a metric value must use a before/after delta, since counters accumulate across a whole pytest session. `app/main.py`'s `lifespan` calls `session_manager.close_all()` then `await session_manager.wait_closed()` before disposing the database — closing a session's socket does not by itself guarantee the task processing that connection has finished its own cleanup (e.g. marking a device offline), so shutdown must wait for it, not just fire the close.

**The Command Dispatcher (`server/app/dispatcher/`) coordinates, never executes — it never knows command semantics beyond `command_type`/`payload` as opaque values, and never accesses a repository directly.** Its two cross-domain calls are `CommandApplicationService` (every lifecycle transition) and the WebSocket Gateway's `SessionManager` (connectivity check + handing off the envelope) — no other file in the package imports either directly; `dispatcher.py` is the sole composition root that constructs `CommandGateway` (a small wrapper opening one short-lived, transactional `CommandApplicationService` per operation, exactly like `WebSocketGateway` does for `DeviceApplicationService`) and wires it into `worker.py`/`ack_manager.py`/`timeouts.py`/`result_handler.py`. Those four submodules type-hint against `Protocol`s in `interfaces.py` (`CommandLifecyclePort`, `CommandDeliveryPort`) rather than importing `dispatcher.py`'s concrete classes — importing the composition root from the things it composes would be circular. Ack tracking (DISPATCHED → RUNNING, `ack_manager.py`) and execution-timeout tracking (RUNNING → COMPLETED/FAILED/TIMEOUT, `timeouts.py`) are two independent sweep loops, not one: a command is tracked in exactly one of them at a time, handed off via an `on_running` callback rather than a direct import, so `ack_manager.py` never needs to know `timeouts.py` exists either. `retries.py`'s `should_retry(retry_count, max_retries)` must be called with the count *before* incrementing (not the prospective next count) — an off-by-one here silently changes "retry up to N times" into "retry up to N-1 times" and was caught only by a test asserting the exact retry count in a failure message, not by the retry-happens-at-all tests. `CommandDispatcher.health_ok` distinguishes "never started" (no database configured — not a readiness failure) from "started, then stopped" (the worker task died — `/ready` reports `unhealthy`, 503) via a separate `_ever_started` flag, precisely so the existing dependency-free health tests (which never run the lifespan) keep passing.

**Testing the Command Dispatcher: an in-process "reactive fake agent" (a duck-typed WebSocket whose `send_text` inspects the outgoing COMMAND and queues a scripted `COMMAND_ACK`/`COMMAND_RESULT` reply) is far faster and more deterministic than driving a real second WebSocket connection, but it introduces a real race the tests must account for.** Since the fake agent's reply is enqueued synchronously inside `send_text` with no real network latency, it can be processed (published as `CommandAckReceived`, handled by `AckManager.handle_ack`) *before* the dispatcher's own `mark_dispatched()` DB write — which yields control to other tasks while awaiting — has even returned, let alone before `ack_manager.track()` runs. `test_dispatcher_integration.py`'s fake agent works around this with a small `asyncio.sleep(0.03)` before pushing a reply, simulating the real network round-trip a physical device would always have (and which reliably makes this race a non-issue against a real Raspberry Pi, where WiFi/LAN latency dwarfs a local DB commit) — this is a test-harness fix, not a production code change, since introducing speculative pre-write ack-tracking to close the window in `worker.py` creates its own worse race (an ack arriving between tracking and the write's commit, when the command is still statically PENDING in the database).

**Testing the WebSocket Gateway: prefer a direct `gateway.handle_connection(fake_websocket)` call over `TestClient.websocket_connect()` for anything beyond the happy path/auth failures.** `TestClient`'s websocket support runs the ASGI app on a *separate portal thread* with its own event loop. Two consequences to know before adding a test: (1) code that only executes there under-reports in `pytest-cov`, even with `concurrency = ["thread"]` set (see `test_websocket_gateway_direct.py`'s module docstring) — the fix is a duck-typed fake `WebSocket` (`accept`/`receive_text`/`send_text`/`close`) driven directly, on the *same* event loop as the test, no threads or portals involved; (2) far more importantly, `TestClient`'s websocket teardown *cancels* the server-side connection task rather than waiting for it to finish, which can interrupt an in-flight DB write (the gateway's own offline-marking heartbeat) and wedge aiosqlite's connection pool, hanging the whole test process on the next `database.dispose()`. `test_websocket_gateway.py`'s `_settle()` helper works around this for the handful of tests that must go through a real `TestClient` (full REST+WS integration, admin endpoints): it polls `SessionManager.active_task_count` (not `get(device_id) is None`, which goes to zero *before* the trailing offline-marking DB write, i.e. too early) via repeated real HTTP round trips before letting the client/websocket context managers exit.

**Testing pattern:** unit/integration tests spin up a fresh file-backed SQLite DB per test via `Database(...).create_schema_for_testing()` (no Alembic in tests) — this relies on every domain's `models` module already being imported somewhere so its tables are registered on the shared `Base.metadata` first. Tests then use a transaction-scoped `service`/`repository` fixture — see `server/tests/test_devices.py`, `server/tests/test_commands.py`, and `server/tests/conftest.py`. A fixture that shares one session across setup and the test body should catch-and-rollback on teardown commit failure (a test that intentionally triggers and swallows a DB error, e.g. a race-condition simulation, otherwise fails at teardown instead of in the test). When an HTTP-level test seeds data through one session/fixture and then hits the app through a *different* session (e.g. via `app.state.container.database.override(database)`), the seeding session must `commit()` inside the test body before the HTTP calls, not rely on a fixture's deferred teardown commit — otherwise the request runs against a database that doesn't see the not-yet-committed rows. Every behavior change needs tests for failure paths, not just the happy path (this is a stated project requirement, not just a nice-to-have) — the state machine in particular is tested exhaustively (every (current, target) status pair), not just the happy-path transitions.

Application layer tests live in their own files by concern, not folded into a domain's test file: `test_application_services.py` (DTOs, cross-domain checks, event publishing — assert `isinstance(result, SomeDTO)`, never a domain model), `test_auth_application_service.py`, `test_event_bus.py`, `test_application_dto.py` (mappers + `translate_domain_error`), `test_application_validators.py`, and `test_application_interfaces.py` (each interface is a true ABC — cannot be instantiated directly, only a conforming subclass can). To hit a domain-error branch an application service's normal error paths can't reach through real data (e.g. `create_command`'s except clause, now that the domain layer validates nothing that could fail there), subclass the real domain service and override one method to raise — see `_FailingCommandService` in `test_application_services.py` or `_FailingAuthService` in `test_auth_application_service.py` — rather than skipping the branch. The Auth domain itself splits similarly beyond that: `test_auth_jwt.py`, `test_auth_passwords.py`, `test_auth_tokens.py` (+ the permission catalog), `test_auth_repository.py`, `test_auth_service.py`, `test_auth_dependencies.py` (token resolution only), `test_auth_rbac.py` (`RequireRole`/`RequirePermission`, both as direct unit calls and through a real app with throwaway probe routes), and `test_auth_api.py`.

## Hard constraints (from `.github/copilot-instructions.md`)

- The agent (future `agent/`) must never get a PostgreSQL credential or route — it only speaks the versioned WebSocket protocol and an authorized object-storage upload flow.
- GPIO, cameras, and other hardware are touched only through driver adapters; business logic never imports hardware libraries.
- All network I/O is async; blocking hardware work stays behind explicit adapters/executors.
- Every API/WebSocket/config/persistence boundary uses typed Pydantic models — no raw dicts crossing a boundary.
- Model agent requests as commands: UUID, timestamp, status, idempotency behavior, typed payload/result.
- Prefer composition over inheritance; keep functions narrow and explicit about failure.
